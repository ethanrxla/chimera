# Recon Gatherers Integration Plan

## 1. Integration Strategy: Black-Box Adapters

The most effective way to integrate Zypheron-CLI, VibePenTester, and Decepticon is to treat them as black-box tools. We will create individual adapters for each tool that handle executing the tool, capturing its output, and normalizing it into a single, unified data structure called `ReconBundle`.

This approach offers several advantages:

-   **Modularity:** Each tool is isolated within its own adapter, making it easy to update or replace individual components without affecting the rest of the system.
-   **Reliability:** By treating the tools as black boxes, we avoid the complexities of deep integration, reducing the risk of breakage when the underlying tools are updated.
-   **Consistency:** All data, regardless of its source, is transformed into the `ReconBundle` schema, providing a consistent data format for downstream processing, database storage, and front-end consumption.

## 2. Chimera Module Design: `recon_gatherers`

We will create a new module within Chimera to house the recon adapters:

-   **Module Path:** `chimera/chimera-core/chimera_core/modules/recon_gatherers/`

This module will contain the following components:

-   `schemas.py`: Defines the `ReconBundle` data structure.
-   `zypheron_adapter.py`: Adapter for running Zypheron-CLI.
-   `vibepentester_adapter.py`: Adapter for ingesting VibePenTester reports.
-   `decepticon_adapter.py`: Adapter for using Decepticon for analysis and enrichment.

## 3. The `ReconBundle` Schema

All adapters will produce a `ReconBundle` object, which will serve as the single source of truth for recon data. The schema will be defined in `chimera/chimera-core/chimera_core/modules/recon_gatherers/schemas.py`.

```python
from dataclasses import dataclass, field
from typing import List, Dict, Any, Optional

@dataclass
class ObservedAsset:
    type: str  # host, domain, url
    value: str
    source_tool: str

@dataclass
class Service:
    host: str
    port: int
    proto: str
    service: str
    banner: Optional[str] = None
    confidence: Optional[str] = None

@dataclass
class WebEndpoint:
    url: str
    method: Optional[str] = None
    params: List[str] = field(default_factory=list)
    discovered_by: Optional[str] = None

@dataclass
class Finding:
    title: str
    type: str  # vuln, misconfig, info
    severity: str  # none, low, med, high, critical
    confidence: Optional[str] = None
    evidence_refs: List[str] = field(default_factory=list)
    reproduction: Optional[str] = None
    tags: List[str] = field(default_factory=list)
    raw_tool_fields: Dict[str, Any] = field(default_factory=dict)

@dataclass
class Artifact:
    path: str
    kind: str  # stdout, report, pcap, har
    sha256: str

@dataclass
class ReconBundle:
    run_id: str
    target: str
    tool: str
    observed_assets: List[ObservedAsset] = field(default_factory=list)
    services: List[Service] = field(default_factory=list)
    web_endpoints: List[WebEndpoint] = field(default_factory=list)
    findings: List[Finding] = field(default_factory=list)
    artifacts: List[Artifact] = field(default_factory=list)
```

## 4. Adapter Implementation Plan

### 4.1. `ZypheronAdapter` (Primary Recon)

-   **Role:** Perform broad, initial reconnaissance to discover hosts, subdomains, open ports, and basic web information.
-   **Execution:** The adapter will execute `zypheron scan` as a subprocess, capturing stdout, stderr, and any generated output files.
-   **Normalization:** A parser will be developed to extract structured data from the tool's output and map it to the `ReconBundle` schema.

### 4.2. `VibePenTesterAdapter` (Web Vulnerability Findings)

-   **Role:** Ingest structured reports from VibePenTester to add detailed web application vulnerability findings to the `ReconBundle`.
-   **Execution:** The adapter will be designed to parse report files (e.g., JSON, XML, Markdown) generated by VibePenTester.
-   **Normalization:** The adapter will extract findings, evidence, and reproduction steps from the reports and normalize them into the `ReconBundle` format.

### 4.3. `DecepticonAdapter` (Agentic Enrichment)

-   **Role:** Provide analysis and enrichment of existing `ReconBundle` data, suggesting next steps and generating human-readable narratives.
-   **Execution:** This adapter will take a `ReconBundle` as input and use Decepticon to analyze the data.
-   **Normalization:** The output from Decepticon will be captured and added to the `ReconBundle` in fields such as `analysis_notes` or as new, enriched findings.

## 5. Database Schema for Persistence

The normalized `ReconBundle` data will be stored in a relational database (e.g., Postgres/Supabase) with the following schema. This design ensures data integrity and allows for flexible querying.

-   **`runs`**: Stores metadata about each tool execution.
-   **`targets`**: A canonical list of all targets.
-   **`assets`**: A record of all discovered assets (domains, IPs, URLs).
-   **`services`**: Information about open ports and running services.
-   **`findings`**: The normalized findings from all tools.
-   **`evidence`**: Snippets of evidence, like request/response pairs.
-   **`artifacts`**: Pointers to raw output files, with hashes for integrity.

A detailed schema will be documented in `chimera/docs/Recon_Gatherers_DB_Schema.md`.

## 6. Event-Driven Workflow for "Shannon"

To keep the system modular and prevent direct dependencies, we will use an event-driven approach to send data to "Shannon".

1.  **Execution:** An adapter runs a tool and produces a `ReconBundle`.
2.  **Persistence:** The `ReconBundle` is saved to the database, and its artifacts are stored.
3.  **Event Emission:** An event, such as `recon.findings.created`, is emitted with the `run_id`.
4.  **Notification:** A separate `ShannonNotifier` service listens for these events. When an event is received, it queries the database for the relevant `ReconBundle` and sends a formatted summary to "Shannon".

This decoupled architecture ensures that the recon adapters are not responsible for formatting messages for Shannon, making the system more maintainable.

## 7. Implementation Roadmap

1.  **Phase 1: Foundation and `ZypheronAdapter` MVP**
    -   Create the `recon_gatherers` module and `ReconBundle` schema.
    -   Implement the `ZypheronAdapter` to run `zypheron scan` and capture raw output.
    -   Develop a basic parser for the `ZypheronAdapter` to extract observed assets and services.
    -   Set up the database schema and implement the logic to persist `ReconBundle` data.

2.  **Phase 2: `VibePenTesterAdapter` and Enhanced Normalization**
    -   Implement the `VibePenTesterAdapter` to ingest and parse report files.
    -   Enhance the normalization logic to handle detailed vulnerability findings.
    -   Implement the event emission and `ShannonNotifier` workflow.

3.  **Phase 3: `DecepticonAdapter` and Front-End Integration**
    -   Implement the `DecepticonAdapter` for data enrichment.
    -   Develop the API endpoints required for your front-end interface to query the database and present the recon data.
    -   Integrate the front-end with the Chimera back-end.
